(bug) pre-write.mjs file-length gate is blind on CRLF checkouts: postEditLines() reconstructs post-edit text with a raw current.indexOf(ti.old_string), but on a core.autocrlf=true working tree the file on disk is CRLF while the Edit payload's old_string is LF, so indexOf always returns -1. The hook then takes the 'stale match' branch and returns the PRE-edit line count. Two consequences on every Windows/CRLF repo: (1) it hard-BLOCKS any shrinking edit to an already-over-limit file - hit while splitting stiletto crates/stiletto-game3d/src/combat/mod_tests.rs (625 lines), where every Edit that would have cut it to 343 was rejected as 'File length 625 exceeds hard limit 600'; (2) worse, it silently fails OPEN on growth - an Edit that grows a 500-line CRLF file to 900 is measured as 500 and passes, which is exactly the KIT-T121 corridor.rs failure mode that postEditLines was written to close, still live on Windows. The Write path (typeof ti.content === 'string') is unaffected and measures correctly, which is the workaround used. Likely fix: normalize both sides (current and old_string/new_string) to LF before the indexOf/splice, or fall back to a CRLF-swapped old_string when the first indexOf misses.
